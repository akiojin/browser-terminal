# ブラウザターミナル（仮称）設計メモ

- 起案：2026-11-13、本人の発案（「gwt のターミナルのみ版」）
- 状態：設計段階。要決定事項は §8。
- 目的：AI エージェント（アビサル）がブラウザ経由でマシンのターミナルを操作できる、小さな常駐ツール。通常のターミナル.app はエージェントの操作対象にできない（macOS の computer control では app_blocked）ことが動機。2026-11-13 の pmset 対応で「確認だけならエージェントが完結できるはず」という実需が確認できた。

## 1. ゴールと非ゴール

### ゴール
- Mac / Windows / Linux の3 OS で同じ体験：ブラウザの1ページから、そのマシンの本物のシェルを操作できる。
- エージェントが「コマンドを打つ」「出力を正確に読む」ことを確実にできる（これが最重要要件）。
- 導入は単一バイナリを置くだけ。常駐サービス化も選べる。
- セキュリティの既定は閉じる側：外部に開かない、認証必須、監査ログ。

### 非ゴール
- gwt のようなプロジェクト管理・PM・エージェント管理は持たない（ターミナルのみ）。
- リモートアクセス製品（TeamViewer 等）の代替は目指さない。公開ネットワークへの直接公開はしない。
- sudo のパスワードをエージェントが保持・入力することはしない（§6）。

## 2. 利用形態

- マシン上でサーバーを起動 → ブラウザで `http://127.0.0.1:<port>/?token=...` を開く。
- 操作者：
  - 本人（普通のターミナルとして使う）
  - エージェント（本人の Mac の Chrome を computer control で操作して入力欄に打つ／画面のテキストを読む）
  - エージェント（API 経由、§5。採用するかは要決定）
- 複数マシンに置けば、マシンごとに1ページ（タブ）が対応する。

## 3. アーキテクチャ

```
[Browser: 出力ログ(DOMテキスト) + 入力欄]
        ↑ WebSocket（出力ストリーム / 入力 / 制御）
[ローカルサーバー（単一バイナリ)]
        ↑ PTY
[本物のシェル: zsh/bash (Mac/Linux), PowerShell (Windows)]
```

- サーバーが PTY セッションを複数保持し、本物のシェルを常駐させる（セッションはブラウザを閉じても維持）。
- ブラウザのタブごとに別のターミナル（別セッション）を開ける（2026-11-13 10:08 本人要件）。新規タブ＝新規セッションが既定で、既存セッションへの再接続（アタッチ）も選べる。同一セッションへの複数タブ同時アタッチ（共有表示）の扱いは実装時に決める。
- サーバー側にスクロールバック（直近 N KB）とプレーンテキスト transcript をセッションごとに保持する。
- ブラウザ再接続時はスクロールバックを再送して状態を復元する。

## 4. 画面（UI）

エージェントの読み書き確実性を優先し、xterm.js のようなキャンバス描画は採らない。

- 出力：セルグリッド型のターミナルエミュレーションを JavaScript で実装し、DOM テキスト（行 div ＋スタイル span）で描画する。CR／LF／BS／タブ、カーソル移動、行・画面の消去、行・文字の挿入と削除、スクロール領域（DECSTBM）、代替画面（CSI ?1049 等）、DECAWM の折り返しを解釈し、通常のシェル操作（プロンプト、行編集、履歴、補完表示、進捗の \r 上書き）が本物のターミナルと同じ表示になる。ANSI の色は span のスタイルに変換する（決定 D4）。グリッドから流れ出た行はスクロールバックに保持し、ホイール／Shift+PageUp・PageDown で遡って見られる。
- 入力：出力エリアで直接打つ方式（本物のターミナル方式。2026-11-13 に本人が方式変更を決定し、下部の入力欄は廃止）。出力エリアをクリックするとフォーカスが当たり、キー入力がそのまま PTY へ送られる（Enter は \r、矢印・Home／End・Ctrl 系は対応するエスケープ／制御文字）。日本語 IME は隠し textarea と composition イベントで対応し、モバイルではタップでキーボードが出る。ペーストにも対応する（ブラケットペースト有効時は CSI ?2004 のマーカーで包む）。
- カーソル：ブロックカーソルを現在位置に表示する（フォーカス中は点滅、フォーカスを外すと枠のみ）。
- 制御ボタン：割り込み（Ctrl-C）、EOF（Ctrl-D）、画面クリア、再接続、セッション終了。セッションの選択と新規作成もヘッダーに置く。
- 状態表示：接続中／切断とセッション名。現在のディレクトリ、実行中かどうか（プロンプト待ち／実行中）、sudo パスワード待ちの明示は未実装（今後の課題）。

## 5. エージェント向け API（要決定 D2）

画面とは別に、同じ認証で叩ける小さな API を持つ案：

- `GET /api/transcript?since=<seq>`：まだ読んでいない出力をプレーンテキストで返す。
- `POST /api/exec`：コマンド文字列を現在のシェルセッションへ投入する。
- 利点：computer control の画面読み取りに頼らず、エージェントがバイト単位で正確に出力を取得できる。Tailscale 等の閉じた経路越しでも使える。
- 欠点：攻撃面が増える。UI のみ版より認証・監査を厳しくする必要がある。

## 6. sudo と秘密情報

- エージェントは `sudo <cmd>` までは打てるが、パスワードプロンプトが出たら停止し、UI に「パスワード待ち」を明示する。パスワードは本人がその場で入力する（エージェントは見ない・打たない）。
- トークンやパスワードを transcript／監査ログに残さない（パスワード入力中のエコーは PTY 側で自然に無効）。

## 7. セキュリティ

- 既定 bind は `127.0.0.1` のみ。LAN 公開は設定で明示的に有効化した場合だけ。
- 起動ごとに変わる、または固定設定のアクセストークンを必須にする（URL クエリではなくヘッダ／初回入力を推奨。computer control での利用しやすさとの兼ね合いは要検討）。
- 監査ログ：実行したコマンド文字列と時刻をローカルファイルへ（出力は含めない既定）。
- 非常停止：UI とサーバー側の両方にセッション終了ボタンを置く。
- Tailscale 経由で使う場合は bind を Tailscale インターフェースに限定する選択肢を用意する。

## 8. 実装の選択肢と要決定事項

### D1. 実装言語・ランタイム
- **決定（2026-11-13 10:07 本人）：Rust 単一バイナリ**（候補A）。PTY は `portable-pty`。
- 候補A：Rust 単一バイナリ。PTY は `portable-pty`（Unix PTY と Windows ConPTY を統一的に扱える）。gwt と同じスタックで、本人の保守性が高い。本命。
- 候補B：Go 単一バイナリ。Unix は `creack/pty`、Windows ConPTY は別ライブラリで吸収。開発速度は速いが Windows PTY の実績差がある。
- 候補C：Node + node-pty。試作は最速だが、配布にランタイム同梱が必要で常駐ツールとしては重い。
- 推奨：A（Rust）。

### D2. エージェント向け API の有無（§5）
- **決定（2026-11-13 10:07 本人）：持つ。** 既定オフ、設定で有効化（当初の推奨どおり）。

### D3. Windows のシェル
- **決定（2026-11-13 10:08 本人）：PowerShell を既定**（7 があれば 7、無ければ Windows PowerShell）。cmd は選択可。

### D4. ANSI の扱い
- **決定（2026-11-13 10:09 本人）：最初から色も付ける。** UI は ANSI を span に変換して色表示する。ただしテキスト自体は DOM に保持し（エージェントの読み取り確実性を維持）、API／transcript は ANSI を除去したプレーンテキストを返す。

### D5. 常駐方式
- **決定（2026-11-13 10:09 本人）：両対応、既定は手動起動。** OS サービス（launchd・systemd・Windows サービス）登録は選択式。

### D6. ポートとトークンの扱い
- **決定（2026-11-13 10:10 本人）：両方とも固定。** 固定ポート（例：17337）＋設定ファイルの固定トークン（権限 600）。

## 9. スコープ

### v1（最小）
- 3 OS 対応サーバー（単一バイナリ）、複数 PTY セッション（タブごとに別ターミナル、再アタッチ可）、グリッド型ターミナル UI（出力エリアへの直接キー入力）、出力ストリーミング、割り込み／EOF、再接続とスクロールバック、トークン認証、localhost bind、監査ログ。

### v2 候補
- 色付け表示、API（D2 で見送った場合）、ファイル転送は持たない方針を維持。

## 10. 未決・リスク

- Windows の ConPTY はエンコーディング（UTF-8 化）とリサイズ周りに癖がある。実機検証が要る。
- macOS の常駐サービス化は署名・公証の都合で配布形態に影響する（自分用なら回避可）。
- ブラウザタブを閉じてもセッションが残る仕様は便利だが、放置されたシェルの扱い（タイムアウトで終了するか）は要決定。
